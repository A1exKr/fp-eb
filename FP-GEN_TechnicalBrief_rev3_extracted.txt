 Technical Brief: `r`n Fee Proposal Generation System `r`n `r`n Overview `r`n The Fee Proposal Generation System (FP-GEN) is a software tool designed to automatically produce comprehensive fee proposal documents in response to client Requests for Proposals (RFPs). These fee proposals follow a standard structure – including sections such as Cover Letter, Project Understanding, Methodology, Scope and Deliverables, Schedule, Team Structure, Financial Proposal, and Relevant Experience – which are all assembled into a formatted document. The system leverages automation (including Large Language Model integration) to parse the RFP and populate proposal content, uses database-driven data (e.g. staff rates, past project profiles), and employs template-based document generation to ensure consistency and efficiency. This brief details the input requirements, output content, calculation algorithms, user interface design, and automation logic, providing a guide for development and maintenance teams. `r`n `r`n Input Data Requirements `r`n To generate a tailored proposal, the system must gather various input data fields from either the RFP document or internal databases. Each field’s source, format, and necessity are defined below: `r`n Project Information: `r`n Project Name: Extracted from the RFP (e.g. project title or RFP cover) or entered by the user. Text string, mandatory (used throughout the proposal document, especially in the Cover Letter and headers). `r`n Client Name: Obtained from the RFP (client organization issuing the RFP) or user input. Text string, mandatory (used in the Cover Letter salutation and elsewhere). `r`n Project Location: From RFP context or user input – city, country, or region of the project. Text string, optional but recommended (appears in Project Understanding and Relevant Experience matching). `r`n Project Type/Category: Identified from the RFP (e.g. “Master Plan”, “Office Tower Design”) or selected by user. Text, optional (can trigger selection of methodology templates and relevant experience examples). `r`n Site Area/Size: If provided in RFP (e.g. “50 hectares”), numeric with units, optional (included in Project Understanding to demonstrate scale). `r`n Project Duration or Timeline: If RFP specifies a required completion time or schedule (e.g. “complete in 11 weeks”), numeric (weeks or months) or date range, optional (used in Schedule section and to plan phases). `r`n Scope & Deliverables: `r`n Scope of Work Summary: A descriptive summary of what the project entails and what the client expects. Extracted by parsing the RFP’s scope description and requirements. Text (multi-sentence), mandatory (feeds into the Project Understanding section and informs methodology). `r`n Deliverables List: Specific deliverables the client expects (e.g. reports, drawings, models). Extracted from the RFP (often listed in a scope section) or entered by the user if not explicitly stated. Format: a list of deliverable items (bulleted), mandatory (populates the Scope and Deliverables section). `r`n Project Phases/Stages: The phases of work as defined by the RFP or as standard for the project type (e.g. Concept, Detailed Design, etc.). Could include phase names and descriptions. If the RFP outlines a phased approach, those are parsed; otherwise user can define phases. Format: list of phase names (with optional brief descriptions), mandatory for fee breakdown (even if a single phase). `r`n Milestones/Workshops: Key meetings or milestones (such as workshops, presentations, submission dates) expected by the client. Extracted from RFP schedule requirements or set by user based on methodology. Format: list of events with timing, optional (used to enrich the Schedule and Methodology sections). `r`n Team & Resources: `r`n Required Disciplines/Expertise: Based on RFP requirements or project type (e.g. Urban Planning, Architecture, Infrastructure, Landscape). Parsed from RFP if it specifies required expertise, otherwise inferred. Format: list of disciplines, optional (guides team composition and mentioned in Cover Letter and Team Structure). `r`n Proposed Team Members/Structure: The internal team roles proposed for the project. This includes key personnel (e.g. Project Director, Project Manager, discipline leads) and any partner or specialty consultants. Sourced from an internal database of staff or entered by the proposal manager. Format: for each team role, name/title/department; optional but typically provided (populates the Team Structure section and sometimes mentioned in Cover Letter). `r`n Specialty Consultants: Any external specialist firms or consultants to be engaged (e.g. local partners, environmental consultants). Often identified in the RFP or decided by the firm. Format: name of consultant and role (e.g. “Local planning partner”), optional (if none required). These may be included in the Team Structure and noted in the Financial Proposal (usually as separate cost items or exclusions). `r`n Financial Inputs: `r`n Standard Rates for Personnel: Retrieved from the company’s rate database for all relevant staff roles/ranks. Each role has an hourly or daily rate (and possibly an overhead component) defined. For example, the database might list standard hourly rates for ranks like Planner P-ST3 or Architect A-PR4 , including base staff cost and indirect cost. Source: internal database; Format: numeric (e.g. in JPY/hour or per day), required for fee calculations. `r`n Man-Hours or Man-Days by Role and Phase: The estimated effort required, typically provided by the user (project manager) based on scope complexity or historical data. The user will distribute the effort across project phases and team roles. Format: a matrix of hours (or days) with phases as columns and roles as rows, mandatory for fee calculation (the core driver of the Base Fee). `r`n Travel Requirements: Number of trips for project meetings or site visits, and number of people per trip. Either specified in RFP (some RFPs require a certain number of meetings) or estimated by the team. Format: integer counts (e.g. 3 trips, 2 people each), optional (defaults can be 0). Used to calculate reimbursable travel expenses. `r`n Reimbursable Unit Costs: Standard costs for travel and other reimbursables. For example, a fixed rate per person-trip for international travel (e.g. $6,000 per trip) is defined as a constant in the database or configuration. Other reimbursables might include unit costs for printing, courier, etc., if applicable. Format: numeric costs, with currency; optional (required only if such expenses are anticipated). `r`n Sub-consultant Fees: If the project requires external consultants (e.g. local firms for surveys or specialty studies), their fees may be input if known (from their proposals or fee estimates). In many cases, the RFP might not provide this, so the user enters a provisional sum. Format: numeric amount per sub-consultant or total, optional (only if using sub-consultants; included in Financial Proposal breakdown as “Subconsultants”). `r`n Tax Rates: Applicable tax or VAT percentage for the project jurisdiction (from internal knowledge base or user input). Many proposals present fees exclusive of taxes, but the rate is noted for contract purposes. Format: percentage, optional (used to calculate a gross fee if needed or mentioned in conditions). `r`n Currency and Exchange Rates: The primary currency for the fee (e.g. JPY or USD) and any conversion rate if a secondary currency is shown. The system may use JPY internally (for rate consistency) and convert to USD or local currency for client presentation. Source: user input or financial database; Format: currency code and numeric rate, optional (mandatory if output requires multiple currencies). `r`n Reference Projects Data: `r`n Project Profiles Library: An internal database of the firm’s past projects, particularly for Relevant Experience section. Each entry includes project name, location, scale (site area, project size), client name, project type/category, a brief description of the work, and optionally awards or outcome. Format: structured records (text and numeric fields, and images if available). `r`n Selected Relevant Projects: The user (or automatically, based on project type and region) chooses a set of impressive past projects to include. Typically, 10-15 projects for each area of experience are included to demonstrate experience. Each chosen profile provides content for the Relevant Experience section. Source: user selection from database (the RFP itself might suggest areas of experience to highlight, but final choice is by the proposal team). Format: list of project IDs or names to include, mandatory (at least one reference must be included to complete that section). `r`n Each input field above is marked as mandatory if the proposal generation cannot proceed meaningfully without it (e.g. Project Name, Scope Summary, man-hour estimates), or optional if the proposal can still be generated with defaults or omissions (e.g. Site Area, if not given, the proposal will omit that detail). The source indicates whether the data is expected to be parsed from the RFP text, fetched from an internal database, or provided manually by a user. In practice, after the RFP upload, the system will present the parsed results for user verification – the user can confirm or edit these fields before generation. `r`n `r`n `r`n Output Document Sections and Content `r`n `r`n Once the necessary inputs are prepared, the system generates the proposal document’s sections. Each section of the output has defined content with placeholders to be filled by the parsed or input data. Below, we define each section and explain how the system populates it: `r`n `r`n Cover Letter `r`n The Cover Letter is a formal letter addressed to the client, serving as the proposal’s introduction. It appears on the proposal’s cover or first page. The content is semi-static, following business etiquette, but includes dynamic placeholders for project-specific details. Key elements of the cover letter include: `r`n Address and Salutation: Typically starts with “Dear Sirs,” or a specific addressee if known, followed by a brief introduction referencing the project name (e.g., “...invited to submit our proposal for your esteemed project {{Project Name}} .” ). The client name or organization may also be referenced here. `r`n Expression of Honor and Interest: A sentence or two expressing gratitude for the opportunity and the firm’s enthusiasm for the project. `r`n Brief Project Understanding Statement: A custom sentence reflecting an understanding of the project’s nature. For example, the cover letter might mention the project type and site, e.g. “Based on our in-depth understanding of the project, we believe we can establish a solid master plan for the {{Site Area}} site in {{Location}} that offers an attractive environment...” . This shows the client that the team is aware of the project specifics (the system can insert site area and location if available). `r`n Team Introduction: The cover letter often highlights the strength of the proposed team. The system will insert a line about the multidisciplinary team assembled for the project, including key disciplines involved. For instance, an automatically generated line might read: “We have assembled a highly skilled multidisciplinary team of experts in urban planning, architecture, landscape, and infrastructure under the leadership of our top management” . This text can be drawn from a template but will adapt to the disciplines relevant to the project (if the project is, say, an architecture-only project, it might omit unrelated disciplines). `r`n Assurance of Commitment: One or two sentences indicating senior oversight and commitment to deliver (often mentioning a senior executive or project director who will personally oversee the project). In the example content, the letter stated that the project will be overseen by a Senior Executive Officer, emphasizing a high level of commitment. The system can insert the name and title of the executive sponsor for the proposal (from a user profile or database). `r`n Closing and Signature: A polite closing expressing hope to meet the client’s expectations and a forward-looking statement (e.g. looking forward to the opportunity to work together). Then a sign-off with the name, title, and company of the signatory (typically a senior officer). The system can fetch this from a configuration (e.g., the designated signatory’s details). `r`n Population logic: The cover letter content is primarily based on a template which can be stored in the database or as a text snippet in the system. Placeholders like {{Project Name}} , {{Site Area}} , {{Location}} , and references to disciplines or team leader name are replaced with actual data. Some sentences might be conditionally included (for example, mention of site area only if that data is available). The tone remains formal and sincere. The system may use an LLM to refine this section if needed – for instance, it could prompt the LLM with the project specifics and ask for a polite introductory letter. However, a standard template ensures consistency. The user can review and edit the auto-generated cover letter in the Proposal Editor UI before finalizing, to make any project-specific tweaks or ensure the tone fits the particular client. `r`n `r`n Project Understanding `r`n This section demonstrates the consultant’s understanding of the project background, context, and the client’s objectives. It is typically divided into one or two parts: a general Site/Project Information overview, and a Client’s Request or Objectives part. `r`n `r`n Site/Project Information: A narrative description of the project’s context – often including the site characteristics, overall project goals, and key challenges or focuses. The system generates this by analyzing the RFP’s background section. For example, it will mention the site size and location, and the major development themes. In a master plan project, the text might cover the intended development mix (residential, commercial, etc.) and key principles like sustainability or connectivity, as in this example: “The project involves developing a comprehensive master plan for a vibrant and sustainable urban environment, integrating residential, office, and commercial spaces, and embodying principles of Transit-Oriented Development (TOD).” The system can extract phrases directly from the RFP to ensure accuracy (e.g. if the RFP states specific goals, those will be reflected). `r`n Client’s Request/Objectives: This sub-section explicitly enumerates what the client is looking for, if stated in the RFP. It may reiterate the scope in terms of client goals or required outcomes. For instance, the proposal might state: “The client requests a plan that incorporates TOD elements and caters to both current and future community needs, with a strong emphasis on sustainability and smart city methodologies, all within a tight timeline of {{Project Timeline}} ” . Here, {{Project Timeline}} could be “11 weeks” or another duration extracted from the RFP. This part ensures the client sees their key asks mirrored back, demonstrating understanding. `r`n Population logic: The content for Project Understanding is generated by summarizing the RFP . The system’s parsing module, often using a Large Language Model (LLM), identifies relevant portions of the RFP (such as project background, objectives, scope overview) and condenses them. The parsed information is mapped to structured data (e.g., project purpose, key features, timeline). An LLM can then be prompted to compose a concise narrative using those points. Alternatively, the system might use predefined template sentences into which it plugs details – for example, a template for site description and a template for client objectives. In either approach, placeholders like site area, number of hectares, specific development themes, or timeline are inserted from the parsed data. The output text is stored under a key (e.g., {{Project Understanding}} ) and inserted into the document template. The user can edit this section in the Preview Editor if any nuance is missing or to adjust wording. `r`n `r`n Methodology `r`n The Methodology section outlines how the consultant team will execute the project. It typically breaks down the approach into phases or key steps and demonstrates a clear understanding of process and deliverables. The system uses a combination of standard methods and project-specific information to generate this. `r`n A typical methodology for a planning/design project might include steps like: Project Kick-off , Site Analysis , Workshops/Iterative Design Sessions , Concept Development , Refinement with Feedback , Final Proposal and Presentation , and Quality Control . For example, a generated methodology could include: `r`n Project Kick-Off: Organize an initial workshop with the client and stakeholders to confirm the project scope and strategy, and conduct a comprehensive site analysis. `r`n Strategic Workshops: Conduct a series of design workshops to generate and evaluate master plan options, incorporating real-time feedback from the client. (If the RFP mentioned a certain number of workshops or interim presentations, those will be reflected here.) `r`n Conceptual Master Plan Development: Develop multiple master plan options considering key factors such as urban density, transportation, land use, and sustainability. Integrate feedback and ensure compliance with local regulations at this stage. `r`n Client Involvement & Feedback: After presenting initial options, hold follow-up sessions to refine the selected concept with client input. Ensure the evolving design aligns with the client’s vision and technical feasibility. `r`n Finalization & Presentation: Finalize the preferred master plan incorporating all feedback and necessary analyses. Prepare a compelling presentation of the plan, including phasing, infrastructure integration, and expected outcomes. `r`n Quality Control & Delivery: Conduct internal QA/QC to uphold quality standards and confirm that the final outputs meet all requirements and are ready for submission. `r`n These steps are adapted to the project’s specifics. For instance, if the RFP emphasizes environmental sustainability, the methodology will highlight tasks like environmental impact assessments or sustainable design reviews. If a strict timeline is given (e.g. 11 weeks), the methodology may mention fast-track or parallel work streams to meet the deadline. `r`n Population logic: The system will likely have methodology templates for different project types. For example, a master plan project has a known sequence of activities (similar to the example above), whereas an architecture project might have a slightly different set (concept design, schematic design, design development, etc.). The appropriate template is chosen based on the Project Type input. This template is then adjusted: the number of workshops or phases might be updated to match the RFP (e.g., if the RFP explicitly asks for 2 workshops, the system ensures 2 are described). The LLM or rule-based text generator will insert project-specific details where relevant – for instance, naming the project in the objectives, or adding a note about local considerations (if the RFP mentions local codes or authorities, the methodology might include a step for regulatory coordination). All these steps are compiled into a formatted list or paragraph form. The content is stored under the {{Methodology}} placeholder for insertion. Users can edit or reorder steps in the editor if needed, but generally it should cover all standard steps to give the client confidence in the approach. `r`n `r`n Scope and Deliverables `r`n This section details what work will be done (scope) and what tangible outputs will be delivered (deliverables). It is typically presented as a bullet list or numbered list of items for clarity. The content here is drawn directly from the RFP’s stated scope requirements and deliverables, ensuring the proposal aligns one-to-one with the client’s expectations. `r`n Scope of Work: The scope portion enumerates the tasks the consultant will perform. Each task can be a sentence or short paragraph. For example, tasks might include studies, analyses, design tasks, and coordination efforts. If the RFP listed tasks (e.g., “1. Conduct site zoning analysis... 2. Develop functional land-use options... 3. Determine infrastructure requirements...” ), the system will capture those. For instance, a scope item might read: “ 1. Functional Cluster Zoning: Analyze and propose functional zoning clusters for the site (e.g., residential, commercial, civic zones) considering utilities, road networks, and development restrictions.” Another might be, “ 2. Development Phasing Strategy: Identify and describe the main development phases, optimizing use of existing infrastructure and outlining necessary relocations or upgrades of facilities.” Each item corresponds to a requirement in the RFP or a logical task necessary for the project. The numbering and wording should mirror the RFP wording closely to show compliance – often even using the client’s own language where possible (the LLM can help paraphrase if needed for clarity, but important terms will be retained). `r`n Deliverables: Following the scope tasks, a list of deliverables is presented. These are the outputs the client will receive at project completion or at phase milestones. Common deliverables include reports (e.g. Master Plan Report, Environmental Impact Report), drawings (plans, sections, maps), presentation materials, models, etc., depending on the project. The system extracts any explicit deliverable list from the RFP (for example, “Deliverables: a) Interim report, b) Draft master plan, c) Final master plan document, d) 3D digital model, e) Presentation boards.” ). If the RFP isn’t explicit, the system can suggest typical deliverables for the given project type, which the user can then adjust. Each deliverable is listed with a brief description if needed. For example: “ Final Master Plan Report: A comprehensive report including all analyses, plans, drawings, and recommendations for the master plan, in both hardcopy and PDF formats.” Such descriptions ensure the client knows exactly what will be handed over. `r`n Population logic: The LLM-based parser plays a big role here. When the RFP is ingested, the prompt for the LLM includes instructions to extract the scope of work items and deliverables. The parsed output might be structured (e.g., a JSON with arrays for “tasks” and “deliverables”) which the system then formats as list items. The ordering and phrasing follow the RFP closely. The placeholders in the template (e.g., {{Scope And Deliverables}} ) will be replaced by the formatted list of tasks and deliverables. If the RFP text for scope is very verbose (spanning multiple paragraphs or including sub-bullets), the system will condense it to a clear list but still ensure all main points are included. In cases where the RFP scope is vague, the proposal manager may manually enter or edit the scope list to ensure it’s precise. The final content is critical for contractual clarity – it sets the boundaries of work – so the system ensures no item from the RFP is omitted. The user interface will allow reviewing this list before finalizing. `r`n `r`n Schedule `r`n The Schedule section provides an overview of the project timeline and key milestones. It aligns the proposed work plan with the client’s timeframe. In a formatted proposal (especially in slides or Word format), this might be presented as a timeline graphic or table, but the textual description is as follows: `r`n Overall Duration: The total project duration in weeks or months is stated upfront. For example, “ Project Duration: Approximately 11 weeks from kick-off to final submission.” If the RFP gave a specific deadline or duration, that is used; otherwise, the duration is estimated based on the scope (and can be adjusted by the user). `r`n Phase Breakdowns: A breakdown of timeline by phase is provided, often in a table or list. Each project phase (as defined in the scope) will have a start and end or a duration. For example: “ Stage 1 – Concept Development: 13 weeks” , “Stage 2 – Detailed Master Plan: 9 weeks” , etc., reflecting the effort allocated. In the case where multiple phases run sequentially, the timeline may be cumulative (Stage 1: Weeks 1–13, Stage 2: Weeks 14–22, etc.). If some phases overlap, that can be noted as well (though typically for simplicity, proposals assume sequential phases unless otherwise stated). `r`n Milestones and Meetings: Key events are marked on the schedule. For instance, “Kick-off Workshop – Week 1” , “Interim Presentation – Week 8” , “Final Presentation – Week 11” , etc. The example timeline in the Vietnam Master Plan included workshops labeled WS1, WS2, etc., aligned with stages. The system, using either a simple Gantt chart logic or milestone list, will populate these from the Milestones/Workshops input or derived from the methodology steps. `r`n Schedule Chart/Visual (if output format supports it): In a PowerPoint or Word output, this section might include a visual timeline. In the FP-GEN template, for example, a slide showed a week-by-week timeline with markers for workshops. The system can generate this by populating a pre-designed chart or table with the phase names and durations. (For the purpose of this text brief, we focus on the data rather than the graphic.) `r`n Population logic: The schedule is constructed by combining the Project Phases and the Timeline input. If the RFP specified an end date or total duration, the system uses that as the guiding parameter and may distribute time across phases proportionally to their workload (or as indicated in RFP). If not specified, default durations for each phase can be suggested (e.g., Concept: 3 months, Detailed Design: 2 months, etc.) which the user can adjust. The system will ensure that the sum of phase durations equals the overall project duration. It will also insert any specific dates if provided (for instance, “Final submission due by December 2025 ” could be explicitly stated if known). In the template, placeholders like {{Total Duration}} , {{Phase1 Duration}} , {{Phase2 Duration}} , etc., or even an entire pre-formatted schedule table, are replaced with these values. The user can fine-tune the timeline via the UI, especially to adjust overlap or exact milestone weeks. The Schedule section thus communicates a clear plan that aligns with the client’s timeframe. `r`n Team Structure `r`n This section presents the proposed project team and organizational structure for the project. Its purpose is to reassure the client that the right expertise is on board and that roles and responsibilities are clearly defined. The output may be an org chart diagram or simply a list of team members by role, depending on the format. In FP-GEN’s slide format, a visual diagram was used, with placeholders for team roles and logos. `r`n Key elements in Team Structure include: `r`n Key Personnel and Roles: A listing of the main team members and their roles. This typically includes the Project Director/Principal-in-Charge, Project Manager, and Lead specialists for each major discipline involved (e.g. Lead Master Planner, Lead Architect, Lead Infrastructure Engineer, etc.). For each named individual, the title and department can be given. In a text format, this might be bullet points or a simple table (Name – Role). For example: “Wataru Tanaka – Senior Executive Officer (Project Principal)” , “Jane Smith – Project Manager (Urban Planning)” , “John Doe – Lead Architect” , etc. If the output is more visual (like a slide), these might appear in an organization chart layout with hierarchy (Project Principal at top, then project manager, then discipline leads below). `r`n Department/Discipline Grouping: Often, team structure is presented by grouping personnel under their discipline or sub-team. For instance, under “Master Planning – Overall Coordination” , one might list the master planning team members; under “Architecture” list architectural team members, etc. The example text shows categories like Masterplanning , Hotel, Residential which likely correspond to sub-teams or specialist sectors for that project. Our system will generate these groupings based on the Required Disciplines and team input. If a project requires multiple specialized sub-teams (e.g., separate teams for different components like hotel planning, residential planning), those are shown as branches in the structure. `r`n Specialty Consultants and Partners: If external consultants are part of the team, they are included here as well. They might be shown separately (for example, alongside a “Specialist Consultant” label with their logo). In the template, there were placeholders for client and specialist consultant logos, indicating that, for instance, a local consultant’s logo could be placed to show partnership. In text form, we would list the consultant name and role (e.g., “ABC Environmental Ltd – Environmental Impact Assessment Consultant (Specialty Sub-consultant)”). `r`n Client/Stakeholder Representation (optional): Sometimes proposals include the client’s team in the org chart for context. In FP-GEN’s template, a placeholder for (CLIENT) Project Management was present, suggesting the diagram showed how the consulting team interfaces with the client’s project manager. In our system, this could be included if the RFP mentions specific client liaison or if it’s customary to illustrate reporting lines. `r`n Population logic: The Team Structure section is populated from the Team Members input data . The user will have entered or confirmed the list of team members and their roles. The system arranges this information according to a template. For example, the template might have an org chart shape with placeholders like {{Project Director Name}} , {{Project Manager Name}} , {{Discipline1 Lead}} , etc. Those get filled in by matching roles from the input. If an expected role isn’t filled (say no “Landscape Architect” is needed), that placeholder may be removed or left blank. If the output format allows images, the system can also insert profile photos or company logos where appropriate (e.g., the company logo for the prime consultant, client logo, and any partner logos). For a Word document output, a simpler representation (like a bullet list or table of team roles and names) is used, generated via a template. `r`n Crucially, this section may not be heavily auto-generated by AI because it requires accuracy about names and positions – the data comes from the database of staff. However, the system could automatically fetch titles and department names for each person from an HR database. It ensures that all key roles requested by the client (if any were explicitly required in the RFP, such as “Key Expert CVs for Urban Planning and Transportation”) are accounted for in the team structure. The user can review this and adjust assignments before finalizing. `r`n `r`n Financial Proposal `r`n The Financial Proposal section details the fee breakdown and payment terms. It is one of the most critical sections, as it directly addresses the cost of the services. This section typically includes a breakdown of fees by phase or category, totals, and any clarifications on inclusions/exclusions, optional services, and taxes. The system generates this section through calculation algorithms and then formats the output (often as tables or structured text). `r`n `r`n Components of the Financial Proposal: `r`n Fee Breakdown Table: A table or structured list summarizing the fee. This is usually broken down by project phase and/or cost category. For example, a table might have columns for each phase (Stage 1, Stage 2, …) plus a Total column. Rows might include categories like “Nikken (Prime Consultant) Fees”, “Sub-consultants”, “Reimbursable Expenses”, etc., for each phase. Alternatively, the breakdown might list phases as rows with their fee, then additional rows for totals and optional items. `r`n In our context, the system will likely present the fee breakdown by category first, with an overall summary, as in the example: Nikken Subtotal , Overheads , Subconsultants , Production , Travel , etc., culminating in the total fee. For instance, one generated breakdown might be: `r`n Category `r`n Amount (JPY) `r`n Nikken Labor Fee (Base) `r`n ¥12,000,000 `r`n Overheads & Profit `r`n ¥1,999,000 `r`n Sub-consultants Fee `r`n ¥6,6 77 ,000 `r`n Production (e.g. model, etc.) `r`n ¥0 `r`n Travel Expenses `r`n ¥5,244,000 `r`n Total (Lump Sum Fee) `r`n ¥25,9 21 ,000 `r`n (Figures above are for illustration; they match the example where the total fee is ¥25.91 million.) The system can also convert this to another currency if needed (e.g., ≈USD 235,552 in that example) and present both. If breaking down by phase, a separate table might list Phase 1 fee, Phase 2 fee, etc., and their sum equals the base fee. `r`n Calculation Algorithm (Fee Computation): Behind the scenes, the system calculates these figures using input data: `r`n Man-hour Cost Calculation: For each phase and each role, the system multiplies the man-hours (or man-days) by the respective hourly (or daily) rate from the rates database. For example, if Phase 1 involves 20 hours of a Senior Planner (rate ¥16k/hour) and 10 hours of a CAD Technician (rate ¥5k/hour), it sums those costs. This is done for all roles in the phase to get the Phase labor cost . It repeats for each phase. Summing across phases gives the Total direct labor cost for the project. `r`n Overhead/Profit Addition: Depending on the firm’s policy, an overhead or profit margin is added. This could be a percentage of the direct labor cost. In the example, an overhead line item (~¥2 million) was about an 8.3% markup on the base labor subtotal. The system can either calculate this as a fixed percentage (configured in the database, e.g. 10% of labor ) or use the difference between “staff-rate” and “billing rate” if the rates already include overhead. (If the internal database rates already have indirect cost separated, the system might choose to present the breakdown for transparency by splitting out that portion as “Overheads”). `r`n Sub-consultant Fees: If any sub-consultants are involved, their fees (input by the user) are added. They can be distributed by phase if applicable, or listed as a lump sum in one category. The example shows a “Subconsultants Subtotal” of ¥6,666,000 – presumably a known amount or percentage for that project. Our system will simply take the input values for each sub-consultant and sum them (if multiple), or allocate them to relevant phases if the user specifies. `r`n Reimbursable Expenses: Travel and other reimbursables are calculated next. For travel, the formula is: Number of Trips × People per Trip × Unit Cost per Trip . For example, 3 trips × 2 people × $6,000 = $36,000, which would be converted to JPY (and in the example, travel came to ¥5,244k, likely similar logic). The system also includes any other reimbursables (like printing, communications) either as a flat percentage of labor or itemized if provided. In many proposals, travel is the main reimbursable item and is often a significant line. `r`n Contingency/Efficiency Adjustments: Optionally, the system can include an efficiency or contingency factor. In the example sheet, an “Efficiency Target (%) = 54” was listed. This might indicate a planned efficiency saving (e.g., only charging 54% of something) or could be an internal metric. If the firm applies a discount or contingency, the algorithm would adjust the fee accordingly. For instance, if the target efficiency is 90%, the system might reduce the labor hours by 10% in the fee calculation to stay competitive, or explicitly show a discount line.
